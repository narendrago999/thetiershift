MODULE 01FOUNDATION

Microsoft Fabric architecture & end-to-end analytics

Understand the platform before choosing its components. Learn how Fabric brings data movement, engineering, warehousing, real-time analytics and Power BI together.

What Microsoft Fabric is — and what it is not

Microsoft Fabric is a SaaS analytics platform that combines multiple data experiences over a shared foundation. It is not simply a renamed data lake, a single Spark cluster or a replacement for every operational database. The platform provides specialised workloads that work together: Data Factory for movement and orchestration; Data Engineering for Spark-based processing; Data Warehouse for SQL-centric analytical storage; Real-Time Intelligence for event-oriented workloads; Data Science for model workflows; and Power BI for semantic modelling and reporting.

Engineering lens: Start with the business requirement, latency, data volume, skills, security and operating model. Only then select the Fabric item. A low-code pipeline and a PySpark notebook are alternative tools for different transformation needs—not competing religions.

Think about it

A company needs daily ERP extracts, near-real-time machine telemetry and governed executive reporting. Which parts are batch, which are streaming, and which consumers need curated data?

The shared platform model: workloads, items and OneLake

Fabric experiences are organised around workspace items. A workspace is a collaboration and lifecycle boundary; items are the resources inside it, such as lakehouses, warehouses, notebooks, pipelines and semantic models. OneLake provides the logical data lake foundation for the tenant. The goal is to make data available across experiences without designing a separate copy for every engine.

Do not confuse a shared storage foundation with automatic permission equivalence. Access to an item and access to specific data can involve different permission layers. Security must be designed and tested for the actual access path.

Choose the right workload and data store

Use a lakehouse when file-based data engineering and Spark-based transformation are central. Use a warehouse when relational SQL modelling and T-SQL-centric consumption are primary. Consider event-oriented capabilities for streaming scenarios. A solution can combine items; it does not have to force every workload into one object.

  • Data Factory: ingest, copy, orchestrate and schedule.
  • Lakehouse: files, Delta tables and Spark engineering.
  • Warehouse: SQL-first analytical warehousing.
  • Semantic model: business measures, relationships and governed BI consumption.
Practical task

Write a one-page architecture decision for a finance reporting workload. State the data volume, refresh frequency, transformation complexity, SQL needs and chosen Fabric items. Explain one alternative you rejected.

MODULE 02FOUNDATION

Workspaces, capacity, environments & project setup

Set up a manageable development environment, understand capacity and plan the boundaries that keep teams productive.

Workspaces and item organisation

Workspaces organise collaboration, ownership and access. They should reflect a coherent solution, team boundary or lifecycle stage—not become a dumping ground. Define naming conventions for workspaces and items, owners, descriptions, contacts and lifecycle responsibilities. Decide early whether dev, test and production are separate workspaces or whether a different governed strategy is appropriate.

A practical convention might be ws_sales_analytics_dev, lh_sales_bronze, lh_sales_silver, nb_sales_transform_silver and pl_sales_orchestration. Treat this as an example, not a Microsoft-mandated naming standard.

Practical task

Create a workspace and item inventory with environment, owner, purpose, criticality and deployment approach columns.

Capacity, consumption and workload planning

Fabric capacity provides compute resources shared by workloads assigned to it. Capacity planning is not just estimating row counts: consider concurrency, Spark startup and execution, pipeline schedules, interactive BI, peak windows, data refresh deadlines and workload isolation. Understand your organisation's capacity model and monitoring tools before promising an SLA.

Do not copy a capacity SKU recommendation from a blog and treat it as universal. Benchmark representative workloads, observe utilisation and throttling, account for concurrent activity and revisit sizing as usage changes.

Practical task

Prepare a workload calendar for a 30-minute SLA pipeline, hourly dashboards and a nightly large Spark transformation. Identify possible contention windows and mitigations.

Environment strategy and repeatability

Development should be safe to experiment in; test should validate release candidates with representative configuration; production should be controlled and observable. Separate environment-specific values—connections, workspace references, paths and parameters—from transformation logic. Maintain a clear ownership and promotion process.

Architecture decision record

For each significant choice, record context, decision, alternatives, consequences, owner and date. This helps future engineers understand why the platform looks the way it does.

MODULE 03CORE

OneLake, lakehouse fundamentals & storage design

Understand the file and table layers, paths, shortcuts, Delta storage and how analytical engines access the same data.

Lakehouse structure: Files and Tables

A Fabric lakehouse provides a data lake-oriented experience with a managed table layer. The Files area is useful for landing source files and working with file-oriented data. The Tables area exposes managed analytical tables, commonly stored in Delta format. Keep raw source artefacts distinguishable from curated tables. Define a clear folder convention such as Files/landing/erp/orders/ingest_date=2026-11-13/.

Do not assume that every file in Files is automatically a registered table. A file can exist in OneLake without being registered in the lakehouse table metadata. Understand the difference between a file path and a table name.

Practical task

Create a lakehouse and inspect the Files and Tables areas. Upload a small CSV into Files, then load it as a Delta table and compare how each appears.

OneLake paths, shortcuts and data reuse

OneLake provides a logical namespace for Fabric data. Shortcuts reference data stored elsewhere without creating a second physical copy at the shortcut location. They are useful for data reuse and domain-oriented access, but they do not remove the need to understand source availability, credentials, access controls, network conditions and lifecycle dependencies.

Choose between copying and referencing based on ownership, latency, transformation needs, governance, source reliability and operational responsibility. A shortcut is not automatically the right choice simply because it avoids a copy.

Practical task

Compare a copied source extract with a shortcut-based design. Document data freshness, access, failure dependency and cost considerations.

Delta Lake and Parquet: the essential model

Parquet is a columnar file format. Delta Lake adds a transaction log and table protocol around data files, enabling transactional table operations, schema enforcement and evolution, history and reliable concurrent workloads. In Fabric lakehouses, Delta is the default table format for managed tables. This matters because different Fabric experiences can work with the same table representation.

Remember the conceptual distinction: a Parquet file is a data file; a Delta table is a dataset governed by a transaction log and metadata. Do not manually edit Delta transaction log files.

MODULE 04CORE

Data ingestion with Data Factory, Copy activity & Dataflows Gen2

Design robust source-to-lake ingestion with full and incremental loads, parameters, retries, metadata and monitoring.

Choose an ingestion pattern

First classify the source: relational database, SaaS application, API, file drop, event stream or another lake. Then determine whether the load is full, incremental, change-data-capture-based or event-driven. Consider source limits, connectivity, authentication, network restrictions, extraction windows and restart behaviour.

  • Full load: useful for small reference datasets or initial snapshots.
  • Watermark load: extracts records after a saved timestamp or sequence value.
  • CDC: captures inserts, updates and deletes when the source and connector support it.
  • File arrival: processes new files based on a controlled naming and arrival contract.

Incremental logic must define how late-arriving updates, deletes, duplicate events and failed runs are handled. A timestamp filter alone does not solve all change-tracking problems.

Pipeline Copy activity and parameters

Use pipelines to orchestrate data movement and dependent activities. Copy activity connects to a source and destination, applies configured mapping and conversion, transfers data and exposes execution details. Parameterise reusable pipelines with source object, destination path, load type, watermark column and environment-specific connection references.

For metadata-driven ingestion, store configuration in a control table or file rather than hardcoding every source into separate pipelines. Keep secrets in approved connection/credential mechanisms; never put passwords or keys in notebook cells, source control or pipeline expressions.

Illustrative metadata configuration
{
  "source_schema": "sales",
  "source_table": "orders",
  "load_type": "incremental",
  "watermark_column": "modified_at",
  "target_path": "landing/sales/orders",
  "is_active": true
}
Example configuration only. Adapt the schema and parameter binding to the chosen Fabric item.

Dataflows Gen2, Copy jobs and when to use them

Dataflows Gen2 provide a Power Query-based data preparation experience. They can be suitable when transformations are naturally expressed as Power Query steps and the team benefits from a low-code interface. Copy jobs provide a dedicated data movement experience, including full and incremental copy patterns where supported. Pipelines are useful for orchestrating multiple activities and dependencies.

Choose the item that fits the workload, source support, transformation complexity, operational needs and current product capabilities. Connector support and feature availability can change; verify the current connector matrix before designing around a source.

Practical task

Ingest one CSV and one relational table. Record why you selected Copy activity, Copy job or Dataflow Gen2 for each. Capture source count, destination count, duration and error details.

Reliable loads: idempotency, retries and watermarks

A robust ingestion process can be safely rerun. Use deterministic batch identifiers, staged writes, deduplication keys and explicit load status. Advance a watermark only after the destination write and validation succeed. If a pipeline fails after copying but before updating control state, the retry should not silently create duplicates.

Watermark rule

Persist the last successfully committed watermark—not merely the maximum value observed in a partially processed source extract.

Practical task

Simulate a failure after data copy but before watermark update. Design the retry so that the next run safely processes the same range without double counting.

MODULE 05CORE

PySpark & notebook engineering

Use Spark DataFrames and SQL to process data at scale, write reusable transformations and understand distributed execution.

How Spark executes your code

Spark distributes work across executors. Transformations such as select and filter are generally lazy: Spark builds a logical plan and executes when an action requires a result. A shuffle redistributes data between partitions and can be expensive. Understand the difference between narrow transformations, wide transformations, partitions, stages and tasks before trying to optimise code.

Do not call collect() on a large DataFrame just to inspect it. Use bounded operations such as show(), limit() and carefully selected aggregates. Avoid Python UDFs when built-in Spark SQL functions can express the same logic.

Read, inspect and transform a DataFrame

Start by inspecting schema, sample rows and source quality. Define explicit schemas when practical, especially for financial amounts, identifiers and dates. Avoid relying on automatic inference for production-critical fields: inconsistent source values can lead to unexpected types.

PySpark — read and inspect a CSV file
from pyspark.sql import functions as F
from pyspark.sql.types import (
    StructType, StructField, StringType,
    DecimalType, TimestampType
)

schema = StructType([
    StructField("order_id", StringType(), False),
    StructField("customer_id", StringType(), True),
    StructField("amount", DecimalType(18, 2), True),
    StructField("modified_at", TimestampType(), True)
])

orders = (
    spark.read
    .option("header", True)
    .schema(schema)
    .csv("Files/landing/orders/")
)

orders.printSchema()
orders.show(10, truncate=False)

The path above is illustrative: update it to the actual lakehouse attachment and folder structure in your workspace.

Clean data with built-in functions

Standardise strings, parse dates, cast numeric types, handle nulls and define business rules explicitly. Do not convert every column to a string by default; preserve meaningful types and precision. For currency, use decimal types rather than floating-point types when exact decimal arithmetic is required.

PySpark — standardise and validate
clean_orders = (
    orders
    .withColumn("order_id", F.trim("order_id"))
    .withColumn("customer_id", F.trim("customer_id"))
    .withColumn("amount", F.col("amount").cast("decimal(18,2)"))
    .filter(F.col("order_id").isNotNull())
    .filter(F.col("amount") >= 0)
)

quality_summary = clean_orders.agg(
    F.count("*").alias("row_count"),
    F.sum(F.when(F.col("customer_id").isNull(), 1)
          .otherwise(0)).alias("missing_customer_count"),
    F.sum("amount").alias("total_amount")
)
display(quality_summary)

Joins, deduplication and window functions

Before joining, understand the grain and uniqueness of both datasets. A many-to-many join can multiply rows and inflate totals. Profile key counts, define the intended relationship and validate row counts before and after the join. For latest-record deduplication, use a deterministic ordering that includes a tie-breaker.

PySpark — deterministic latest record
from pyspark.sql.window import Window

w = Window.partitionBy("order_id").orderBy(
    F.col("modified_at").desc_nulls_last(),
    F.col("source_sequence").desc()
)

latest_orders = (
    clean_orders
    .withColumn("row_num", F.row_number().over(w))
    .filter(F.col("row_num") == 1)
    .drop("row_num")
)
Practical task

Create a customer-order join. Check the uniqueness of customer_id first, then reconcile order count and amount before and after the join. Explain any difference.

MODULE 06CORE

Delta Lake, medallion architecture & incremental transformation

Build Bronze, Silver and Gold layers with schema control, MERGE operations, historical tracking and quality gates.

Design the medallion layers

Medallion architecture is a logical pattern for progressively improving data quality and usability. Bronze preserves source-aligned data and ingestion context. Silver applies standardisation, validation, deduplication and integration. Gold presents business-oriented models, aggregates and data products. It is a design pattern, not a requirement to create exactly three physical lakehouses in every solution.

  • Bronze: source fidelity, traceability, ingestion timestamp, source file and batch ID.
  • Silver: conformed types, standard keys, quality rules, deduplicated entities.
  • Gold: business grain, facts, dimensions, aggregates and consumer-ready contracts.
Practical task

Draw the path from ERP and CRM extracts to a sales reporting model. Label the transformations and data quality rules at each layer.

Write Delta tables and manage schema

Delta tables support transactional writes and schema controls. Decide whether a write is append, overwrite or merge/upsert. Use schema enforcement to detect unexpected changes; permit schema evolution only through a reviewed contract and migration plan. Uncontrolled automatic schema changes can break downstream consumers.

PySpark — write a curated Delta table
(latest_orders
 .write
 .format("delta")
 .mode("overwrite")
 .option("overwriteSchema", "true")
 .saveAsTable("silver_orders"))
Illustrative initial build. Do not use overwrite blindly for incremental production loads; choose a write strategy that matches the table lifecycle.

Incremental upserts with MERGE

For a dimension or current-state table, merge incoming changes using a stable business key and a clear update policy. Ensure the source contains at most one applicable row per merge key, or resolve duplicates before the merge. Handle deletes and late-arriving updates explicitly.

Delta MERGE — conceptual SQL example
MERGE INTO silver_customer AS target
USING staged_customer AS source
ON target.customer_id = source.customer_id
WHEN MATCHED
  AND source.modified_at > target.modified_at
  THEN UPDATE SET *
WHEN NOT MATCHED
  THEN INSERT *;
Confirm the exact SQL syntax and supported clauses for the Fabric execution surface you use. Validate source uniqueness before merging.

Slowly changing dimensions and historical truth

Type 1 overwrites an attribute when historical values are not needed. Type 2 preserves history by creating a new version with effective-from, effective-to and current-row indicators. Choose the method based on the analytical question. A Type 2 implementation needs deterministic change detection, one current row per business key, correct interval boundaries and a policy for late-arriving changes.

Practical task

Implement a customer Type 2 dimension for customer_id, region and segment. Demonstrate a region change and prove that historical orders still resolve to the correct customer version.

MODULE 07INTERMEDIATE

Data modelling, SQL analytics endpoint & consumption

Shape curated data around business grain and make it useful to analysts and reporting teams.

Define grain before designing facts

Grain is the precise meaning of one row in a fact table. For example, one row per sales order line is not the same as one row per order or one row per daily customer summary. Declare grain first, then choose measures and dimensions. Store additive measures where possible and document semi-additive or non-additive measures such as balances and ratios.

Practical task

Define the grain for invoice line, rental asset daily snapshot and monthly revenue summary. List the dimensions and measures appropriate to each.

Star schema and conformed dimensions

A star schema places a fact table at the centre, surrounded by dimensions that describe the business event. Use surrogate keys where needed, define unknown-member handling and decide how historical attributes should be represented. Conformed dimensions allow different facts to share consistent definitions for customer, product, date or location.

SQL analytics endpoint and semantic model choices

The lakehouse SQL analytics endpoint provides a SQL-oriented way to query supported lakehouse tables. It is intended for analytical querying and should not be confused with a general-purpose transactional write surface for every table operation. Understand the capabilities and limitations of the specific endpoint and item type you are using.

Power BI semantic models add business relationships, measures, security and a governed consumption layer. Decide whether the reporting team should use a managed semantic model, Direct Lake, Import or DirectQuery based on the workload and current support matrix. Avoid assuming every storage mode behaves identically.

SQL — business-level aggregation
SELECT
    d.calendar_year,
    c.customer_segment,
    SUM(f.net_amount) AS revenue,
    SUM(f.quantity) AS units
FROM dbo.fact_sales_line AS f
JOIN dbo.dim_date AS d
  ON f.date_key = d.date_key
JOIN dbo.dim_customer AS c
  ON f.customer_key = c.customer_key
GROUP BY
    d.calendar_year,
    c.customer_segment;

MODULE 08INTERMEDIATE

Pipeline orchestration, parameters & operational patterns

Coordinate notebooks, copy activities, dependencies, schedules, notifications and reusable metadata-driven workflows.

Build an end-to-end pipeline

Orchestration coordinates work; transformation logic performs the data change. Keep responsibilities clear. A pipeline can validate inputs, copy source data, call a notebook, execute downstream activities, evaluate quality outputs and notify an operator. Define dependencies and failure paths explicitly. Avoid building a single giant pipeline that nobody can troubleshoot.

Practical task

Create a pipeline with a source copy, notebook transformation and validation step. Add success and failure paths and record the run ID for traceability.

Metadata-driven pipeline design

Use a configuration table to define source object, destination, load type, watermark, key columns, active flag and transformation notebook. A parent pipeline can iterate over active entries and pass parameters to a reusable child pattern. Keep exceptions explicit: a source requiring special handling should not be forced into an abstraction that hides critical logic.

Retries, dependencies and failure recovery

Retries are appropriate for transient failures, not invalid data or broken contracts. Use bounded retry counts and backoff where supported. Store operational state in a durable control location. A retry must not duplicate business events or skip unprocessed ranges. Distinguish technical success from business success: a pipeline can finish successfully while loading zero rows unexpectedly.

Production rule

Every critical pipeline needs a defined owner, expected schedule, freshness objective, failure notification, restart procedure and evidence of successful data validation.

Streaming foundations: Eventstream, Structured Streaming & KQL

Not every data product can wait for a nightly batch. Streaming systems process continuously arriving events and require explicit decisions about event time, processing time, late arrivals, duplicates, ordering, windowing and checkpoint/recovery. In Fabric, evaluate Real-Time Intelligence capabilities such as Eventstream and Eventhouse alongside Spark Structured Streaming. Choose the engine based on latency, event volume, transformation complexity, operational skills and the downstream consumer.

KQL is designed for querying event-oriented data. A time window groups events into intervals so teams can calculate metrics such as average temperature, event counts or error rates over time. Define the window and timestamp semantics carefully; a five-minute bin is not the same as a five-minute processing delay.

KQL — illustrative five-minute telemetry aggregation
Telemetry
| where Timestamp > ago(1h)
| summarize avg(Temperature) by DeviceId, bin(Timestamp, 5m)
| order by Timestamp desc
Practical task

Design a telemetry solution for 5,000 devices. Specify ingestion, event schema, timestamp field, window size, late-event policy, alert threshold, storage destination and consumer. Explain why you chose Eventstream, Spark Structured Streaming or a batch pipeline.

MODULE 09ADVANCED

Security, governance, lineage & responsible access

Protect the platform at workspace, item and data levels. Build governance that is enforceable and testable.

Workspace roles and item permissions

Fabric workspace roles define what users can do within a workspace. The common roles are Admin, Member, Contributor and Viewer, each with different capabilities. Apply least privilege: not every consumer needs workspace authoring rights. Use security groups where appropriate, review access regularly and separate administrative duties from day-to-day development.

Workspace permissions and data-level access are related but not identical. Understand inherited access and validate effective permissions from the user's actual identity and access path.

OneLake security and data-level controls

OneLake security provides a data-plane model that can scope access to data within supported items. Distinguish management permissions from data access. Apply table, folder, row or column controls only where supported by the specific item and feature. Test access through the engines your users actually use; do not assume a permission tested in one interface proves all paths are secure.

Practical task

Create a role matrix for finance, sales and data engineering personas. State which workspace role and data access each needs, and identify how you will test it.

Governance, sensitivity, lineage and secrets

Governance includes ownership, business definitions, classification, retention, lineage, data quality and change management. Maintain a glossary for key measures and data entities. Record lineage from source to curated table to semantic model. Protect credentials using supported connection and secret-management features. Avoid embedding secrets in notebooks, parameters, Git repositories or logs.

Governance is operational

A policy without an owner, enforcement mechanism, exception process and review cadence is only documentation.

MODULE 10ADVANCED

Performance optimisation, monitoring & cost awareness

Diagnose bottlenecks with evidence. Improve Spark, Delta, pipeline and capacity behaviour without premature tuning.

Diagnose Spark workload performance

Start with the execution plan and Spark UI or available monitoring views. Look for skewed partitions, expensive shuffles, repeated scans, excessive file counts, poor join strategy and unnecessary Python-side processing. Filter early when it reduces data movement, project only needed columns and use built-in functions. Broadcast joins can help when one side is genuinely small enough; do not force them without checking size and memory implications.

Practical task

Take a slow join and inspect its plan. Compare row counts, partition behaviour and runtime before and after a justified change. Document the evidence.

Delta layout, small files and table maintenance

Too many tiny files can increase planning and read overhead. Large unbalanced files can also create inefficient workloads. Understand the platform's table maintenance and optimisation capabilities, including the current support for compaction and layout features. Avoid blindly partitioning by high-cardinality columns: partition design should match common filters, table size and write patterns.

V-Order and other Fabric optimisations are platform-specific. Verify current behaviour and applicable workloads in Microsoft's documentation before changing settings.

Monitoring, capacity and cost governance

Monitor pipeline activity duration, throughput, failures, row counts and data freshness. For Spark, record job duration, input/output volume and failure causes. At the platform level, review capacity utilisation and concurrent workloads. Cost control comes from right-sizing, scheduling, eliminating redundant work, controlling retention and understanding which workloads share capacity.

Practical task

Design a daily operations dashboard with pipeline success rate, freshness SLA, row-count variance, Spark duration, failure count and capacity indicators.

MODULE 11ADVANCED

Git integration, CI/CD, testing & release management

Version your solution, validate changes and promote tested assets between environments with controlled releases.

Version control and collaboration

Use Git to track supported Fabric item definitions and code artefacts. Agree branch conventions, pull-request reviews, naming and ownership. Not every item or property behaves like a conventional source-code file; verify supported item types and known limitations. Keep notebooks and pipeline definitions reviewable, and avoid committing credentials or sensitive sample data.

Deployment pipelines and environment configuration

Separate development, test and production. Promote a known version through validation gates. Environment-specific references and parameters must be mapped deliberately. After deployment, verify that connections, permissions, schedules and orchestration references are correct. Deployment of an item definition does not always mean its data is populated or its dependencies are ready.

Release principle

Promote the exact version that passed testing. Do not make untested changes between test sign-off and production deployment.

Testing and operational readiness

Use layered tests: unit tests for transformation functions; data tests for uniqueness, nulls and accepted values; integration tests for source and destination behaviour; reconciliation tests for row counts and business totals; and end-to-end tests for freshness and consumer outputs. Create a runbook with deployment steps, rollback considerations, ownership, incident severity and recovery actions.

Practical task

Prepare a release checklist that covers code review, tests, data validation, security, schedule, monitoring, owner sign-off and rollback plan.

Database projects, Apache Airflow & platform auditability

Modern Fabric engineering may involve more than notebooks and pipelines. Database projects support source-controlled database development and deployment workflows for supported database items. Apache Airflow workspace capabilities can orchestrate directed acyclic graph (DAG) workflows where that operating model fits. Audit logs and monitoring provide evidence of activity and help teams investigate access, configuration and operational changes.

Before adopting a capability, check current item support, workspace prerequisites, region availability and preview/GA status. Do not assume every database object, Airflow integration or deployment action has identical support across Fabric workloads.

Practical task

Extend your release architecture with one database project, one orchestration DAG use case and an audit evidence plan. Record which artefacts are version-controlled, how secrets are protected and who approves production changes.

MODULE 12CAPSTONE

Capstone: Build an enterprise-ready sales lakehouse

Bring the full course together in one end-to-end project. This is the portfolio artefact that demonstrates applied understanding.

Scenario, requirements and source contracts

You are building an analytics platform for a fictional distributor. Sources include ERP sales orders and invoices, CRM customers, product master files and daily inventory snapshots. Business users need daily revenue, margin, product performance, customer segmentation and inventory availability.

Define source owners, refresh cadence, primary keys, change tracking, expected row volumes, data classification, business definitions and reconciliation totals. Create a source-to-target mapping before building pipelines.

Build Bronze and Silver layers

Land source data with ingestion metadata: source system, file name, ingestion timestamp, batch ID and source modification timestamp. Preserve raw evidence. In Silver, standardise names and types, resolve duplicates, validate keys, handle late arrivals and apply customer/product history rules. Keep invalid records visible in a quarantine or exception path rather than silently dropping them.

Example data quality checks
-- Example validation query
SELECT
  COUNT(*) AS row_count,
  COUNT(DISTINCT order_line_id) AS distinct_lines,
  SUM(CASE WHEN order_id IS NULL
           THEN 1 ELSE 0 END) AS missing_order_ids,
  SUM(net_amount) AS net_revenue
FROM silver_sales_order_line;

Publish Gold, orchestrate and validate

Create fact_sales_line with a clearly declared grain, plus conformed date, customer and product dimensions. Build Gold measures for net revenue, cost, gross margin and units. Orchestrate the daily load with parameters and dependencies. Validate record counts, financial totals, duplicate keys, referential integrity and freshness. Publish a governed semantic model and a concise report.

Deliver the production handover pack

Your submission should include architecture diagram, workspace/item inventory, source mapping, data dictionary, pipeline design, notebook code, quality rules, reconciliation evidence, security matrix, monitoring dashboard, deployment plan, cost assumptions, runbook and known limitations.

Capstone acceptance criteria

A reviewer must be able to understand the architecture, rerun the pipeline, verify the business totals, trace a metric to its source and identify who owns the solution.
