OneLake Shortcuts: Architecture, Security and Design

Design OneLake shortcuts across Fabric and external storage with clear ownership, permissions, caching, lineage and operational controls.

By TierShift Technologies · Published 12 November 2026 · 11 min read

OneLake shortcuts let Microsoft Fabric workloads reference data stored in another OneLake location or supported external storage without creating a conventional second copy. That can simplify data sharing and reduce duplicate ingestion, but a shortcut is not simply a file path alias. Its source identity, target permissions, caching behaviour, ownership and lifecycle all affect the design.

Start with a shortcut

If consumers should read the producer-owned data in place and accept source availability and schema contracts, a shortcut can avoid a redundant ingestion copy.

1. Understand the shortcut model

A shortcut is an object in OneLake that points to a target path. The location where the shortcut appears is the shortcut path; the location it references is the target path. To a consumer, the shortcut can appear as a folder or table in the lakehouse namespace, while the underlying data remains at the source.

This distinction is important operationally. Deleting the shortcut object does not normally delete the target. However, deleting a file or folder through a shortcut can delete the corresponding target data when the caller has sufficient write permissions. Treat shortcut paths as real access paths to source data, not as harmless copies.

2. Choose the right location and source pattern

Shortcuts can reference data within OneLake and supported external locations such as Azure Data Lake Storage and Amazon S3. In a lakehouse, shortcuts under the Tables area can expose supported Delta tables as tables, while shortcuts under Files are useful for file-oriented access and formats that are not discovered as Delta tables.

Use a shortcut when the consumer needs to read data in place and the source can remain the system of record. Use a managed copy when the consumer requires independent retention, heavy transformation, a stable snapshot, isolation from source changes or predictable local performance. The choice should be based on ownership and workload requirements, not on a blanket rule that copies are always bad.

3. Design a producer-consumer contract

Before creating shortcuts across teams, agree a producer-consumer contract. The producer owns source quality, schema evolution, availability and meaning. The consumer owns its transformations, semantic layer and downstream service levels. Define who can change the target path, how breaking schema changes are communicated, and how deprecation works.

Use stable folder structures and predictable naming. Avoid making downstream workspaces depend on personal storage paths or undocumented folder layouts. Record the source workspace or storage account, target path, connection owner, business owner, data classification and expected freshness in a catalogue or operational registry.

4. Understand security at both ends

Shortcut access is governed by permissions on both the shortcut path and target path. In general, the most restrictive permission applies. A consumer with broad permissions on the lakehouse should not automatically gain write access to a source that grants only read access.

External shortcuts can use passthrough or delegated authentication depending on the source and connection pattern. Passthrough uses the caller's identity at the target. Delegated authentication uses an intermediate identity or connection, separating source access from each consumer's personal credentials. Cross-tenant OneLake shortcuts use delegated authentication.

Be particularly careful with semantic models and query engines that use delegated identity modes. Microsoft documents scenarios where the target is accessed using the item owner's identity rather than the end user's identity, while OneLake security roles still filter what the end user can see. Test the actual engine, identity and role combination. Do not infer end-user access from a successful test performed by a workspace admin.

5. Use caching intentionally for external data

Shortcut caching can reduce repeated cross-cloud reads and egress costs for supported shortcut types. The cache is configured at workspace level and has a retention period. It is not a general-purpose guarantee that every external source will be cached: support varies by source and authentication pattern, and files above the documented size threshold may not be cached.

Evaluate caching with real access patterns. Frequently accessed reference data may benefit; rapidly changing operational data may need a different freshness strategy. Document the acceptable data latency, cache retention and process for resetting cache when required. Do not promise real-time synchronisation simply because a shortcut points to a live source.

6. Plan for schema changes, deletions and broken targets

Shortcuts can reflect source updates, but propagation timing can vary with source performance, cached views and connectivity. A renamed or deleted target path can break the shortcut. Schema changes may affect Spark notebooks, SQL consumers and semantic models differently.

Build checks that validate shortcut existence, target reachability, expected table names and key columns. For important datasets, run schema compatibility checks before downstream jobs execute. Have an owner and alert route for broken paths. Treat source deletion and deprecation as a governed change, with downstream impact review.

7. Make lineage and cost visible

Use Fabric lineage views where available, but understand their scope and limitations. Shortcut lineage within a workspace may be visible, while external relationships or certain item types may not appear in the same view. Maintain a simple dependency registry for critical cross-workspace or cross-cloud paths.

Shortcuts can reduce duplication, but they do not eliminate all cost. Query compute, source storage, network transfer, external request charges and caching can still contribute. A workload that repeatedly scans a remote source may be more expensive or less predictable than a curated local copy. Measure the total path, not just the absence of an ingestion pipeline.

8. A practical shortcut governance checklist

  1. Record the producer, consumer, target path, data owner and classification.
  2. Choose the correct location: Tables for supported Delta table discovery, Files for file-oriented access.
  3. Select passthrough or delegated authentication based on the intended identity model.
  4. Test permissions at both shortcut and target paths with consumer identities.
  5. Define schema-change, deletion, freshness and availability expectations.
  6. Measure cross-cloud reads, caching benefits, egress and query performance.
  7. Monitor target health and maintain an impact map for downstream dependencies.

Frequently asked questions

Does a shortcut copy the source data?

No. A shortcut is a reference to a target path. Caching may store accessed files for supported external shortcut scenarios, but that is not the same as creating a separately managed ingestion copy.

Can users write through a shortcut?

That depends on permissions at both the shortcut and target locations and on the source's supported behaviour. Do not assume that a read-only consumer should be able to write through the shortcut.

Should all data be accessed through shortcuts?

No. Some workloads need curated snapshots, independent retention, transformation or predictable performance. Shortcuts are one integration pattern within a broader data architecture.

Conclusion: treat shortcuts as governed data products

OneLake shortcuts are powerful when they connect teams without creating unnecessary copies. Their success depends on more than creating a pointer: establish producer-consumer contracts, test both sides of the permission boundary, design for schema and lifecycle changes, and measure the complete cost and performance path.
