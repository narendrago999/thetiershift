Power BI Direct Lake: Design for Performance

Understand Direct Lake architecture, framing, memory, security and fallback behaviour to build faster Power BI models on Microsoft Fabric.

By TierShift Technologies · Published 12 November 2026 · 11 min read

Direct Lake is one of Microsoft Fabric’s most important options for building analytical models over large Delta tables. It can reduce the need to import a second full copy of data while retaining an in-memory analytical engine for interactive reporting. But Direct Lake is not a switch that automatically makes every model fast. Table layout, model design, capacity, security and query behaviour still matter.

1. Understand what Direct Lake changes

With Import mode, Power BI loads data into a semantic model and maintains an imported copy. With DirectQuery, queries are sent to the underlying source at query time. Direct Lake takes a different path: the semantic model reads Delta tables stored in OneLake and loads the columns it needs into memory as queries require them.

The underlying Delta table is represented by Parquet data files and transaction-log metadata. Direct Lake can load individual columns on demand rather than importing every column in advance. This can make it attractive for large analytical datasets where a full imported copy is expensive or operationally difficult.

A Direct Lake refresh is also different from an Import refresh. It primarily updates the model’s view of the latest Delta table state—often described as framing—rather than copying the entire dataset into the model. The first query that needs a column may still pay the cost of loading that column, so first-query and warm-query performance can differ.

2. Choose the Direct Lake flavour deliberately

Fabric documentation describes Direct Lake on OneLake and Direct Lake on SQL analytics endpoints. They share the goal of querying Delta data with the VertiPaq engine, but their source integration and fallback behaviour differ. Do not treat them as interchangeable labels.

  • Direct Lake on OneLake: connects directly to supported Delta data in OneLake and integrates with OneLake security. It does not use DirectQuery fallback.
  • Direct Lake on SQL: connects through a Lakehouse or Warehouse SQL analytics endpoint. In supported circumstances it can fall back to DirectQuery, including when endpoint features or security behaviour require it.

The choice affects which security features are applied, which source objects are supported, and what happens when a table cannot be served through Direct Lake. Review the current feature comparison for your intended model before standardising on one flavour.

3. Design the Gold layer for analytical consumption

Direct Lake works best when the underlying tables are designed as products for reporting rather than simply exposing every Silver-layer object. Build a Gold layer with clear business grain, conformed dimensions, stable keys, useful date columns and measures that express agreed business definitions.

Prefer a star schema for conventional Power BI analytics. Keep fact tables at a declared grain, avoid unnecessary high-cardinality text columns, and use dimensions to describe business entities. Hide technical columns from report authors where they do not support analysis. A smaller, intentional model is often easier to govern and can reduce the number of columns that need to be loaded.

Where a SQL view is required for a transformation, assess whether it should be materialised as a Delta table for the Direct Lake path you selected. Some view and endpoint scenarios can cause DirectQuery fallback in Direct Lake on SQL. Make the choice explicit and test it with actual report queries.

4. Treat table layout and capacity as model design

Direct Lake has capacity-dependent guardrails, including limits related to Parquet files, row groups, rows and model memory. These are not merely infrastructure details: a table that is poorly maintained can push a model towards fallback, refresh warnings or query pressure.

Small files increase metadata and scan overhead. Excessive row groups and wide tables can increase work when columns are loaded. Use appropriate table maintenance, compact files where justified, and measure the effect of V-Order or clustering against your write and read patterns. Avoid assuming that every optimisation should be enabled on every table.

Capacity memory also matters. Direct Lake loads columns into memory as queries need them, but the model still operates within capacity resource limits. Concurrent models, refreshes, notebooks and data pipelines compete for resources. Review capacity metrics during realistic peak workloads, not only when a single report is tested in isolation.

5. Model security at the correct layer

Security needs to match the Direct Lake flavour and identity path. Direct Lake on OneLake can use OneLake security, while Direct Lake on SQL can interact with SQL analytics endpoint security and may use fallback depending on the configuration. Semantic-model RLS and OLS are separate design choices that must be tested for the actual consumer identity.

Do not assume that a permission configured on one layer automatically protects every other access path. Test with Viewer users, report consumers, service principals and any fixed identity cloud connections used by the model. Confirm that users cannot bypass the intended row or object restrictions through another Fabric experience.

6. Diagnose fallback and slow queries

When a report feels slow, first identify where time is spent. Power BI Performance Analyzer helps isolate visual query durations. DAX Studio or SQL Server Profiler can help inspect model query activity where supported. Fabric capacity metrics can reveal memory pressure and competing workloads.

For Direct Lake on SQL, inspect fallback information rather than guessing. Microsoft documents the TABLE traits diagnostic, including the DirectLakeFallbackInfo column. A fallback may be caused by a source object, security configuration, a table that has not been framed, a transient issue or table guardrails. The correct fix depends on the reason.

Also separate cold-query behaviour from warm-query behaviour. A first query that loads several high-cardinality columns may be slower than a repeated query using columns already in memory. Benchmark representative report interactions, not only one hand-picked DAX query.

7. A practical implementation checklist

  1. Confirm the business use case and select Direct Lake on OneLake or Direct Lake on SQL based on security and source requirements.
  2. Prepare Delta tables with stable schemas, clear grain and a reporting-friendly Gold layer.
  3. Review table file counts, row groups, column cardinality and maintenance strategy.
  4. Design the semantic model with relationships, measures, naming, perspectives and security.
  5. Test first-query and warm-query performance with representative report pages.
  6. Validate security using real consumer identities and all relevant access paths.
  7. Monitor capacity, fallback, model memory, table freshness and user-perceived latency after release.

Frequently asked questions

Does Direct Lake eliminate refresh?

No. It changes what refresh means. Framing updates the model’s view of the Delta table state, but data preparation, metadata updates and model operations still need orchestration and monitoring.

Is Direct Lake always faster than Import?

No universal performance ranking applies to every model. Direct Lake can provide strong interactive performance at scale, but performance depends on table layout, columns loaded, capacity, security and query shape. Benchmark the real workload.

Should every table be Direct Lake?

No. Composite models and other storage modes may be appropriate for smaller reference data, external sources or features that do not fit the Direct Lake path. Choose storage mode per workload requirement.

Conclusion: engineer the path from Delta to DAX

Direct Lake is most effective when the entire path is designed together: well-maintained Delta tables, a purposeful semantic model, the right security model and enough capacity for concurrent workloads. Start with a representative Gold dataset, test real report behaviour, diagnose fallback explicitly and make performance part of the release process.
