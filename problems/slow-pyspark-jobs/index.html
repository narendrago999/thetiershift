01 / THE REAL-WORLD SCENARIO

What is actually going wrong?

A job that runs quickly on a development sample can slow dramatically at production scale. The cause is often data distribution or execution-plan behaviour, not simply a lack of compute.

Symptoms teams commonly notice

  • One or two tasks run far longer than the rest
  • Executors spill heavily or fail with out-of-memory errors
  • Runtime grows sharply as source volume increases
  • A join stage dominates the job despite modest input size
IMPORTANT DISTINCTION

Look beyond the visible symptom.

The first visible failure is not always the root cause. Trace the full workflow, preserve run-level evidence and validate the business outcome before changing production behaviour.

    04 / SOLUTION DESIGN

    How to solve it reliably

    A production solution should address the root cause, make failures observable and support safe recovery.

    1. 01
      Compare the physical plan and Spark UI between fast and slow runs; identify the stage where time accumulates.
    2. 02
      Inspect task duration and input-size distribution to confirm skew before changing partition counts.
    3. 03
      Filter early, project only required columns and avoid repeated actions that recompute lineage.
    4. 04
      Use broadcast joins only when the build side is genuinely small enough for executor memory.
    5. 05
      Apply adaptive query execution where supported, and right-size file layout based on measured workloads.
    IMPLEMENTATION EXAMPLE
    # Inspect the physical plan and avoid scanning unused columns
orders = (spark.read.table("silver.orders")
    .select("customer_id", "order_date", "net_amount")
    .filter("order_date >= DATE '2026-01-01'"))

# Broadcast only when the dimension is small enough for executor memory
result = orders.join(
    F.broadcast(customer_dim),
    on="customer_id",
    how="left"
)
result.explain("formatted")

    07 / PREVENTION CHECKLIST

    Keep the problem from returning

    • Capture a baseline: Record input volume, runtime, stage duration, shuffle and spill.
    • Find the expensive stage: Use Spark UI and explain plans rather than guessing.
    • Change one variable: Test join strategy, filtering, partitioning or skew handling independently.
    • Validate at production scale: Benchmark with representative volume and retain a repeatable performance test.
